Taking the Apothecary off Netlify and onto Cloudflare

Status: open · rewritten Sep 30, 2026 against the repo, live DNS, the Cloudflare account and the Stripe connector · supersedes the Sep 21 draft and absorbs apothecary-domain-move

Goal: the whole app, the shop and the Stripe checkout run from one Cloudflare Worker on apothecaryforest.com, Supabase and Twilio carry on unchanged, and there is no Netlify account left to think about.

What changed since the Sep 21 draft

  • Twelve functions, not ten. create-checkout-session and stripe-webhook landed with the shop.
  • The domain. The target is apothecaryforest.com (registered at Namecheap Sep 30, 2026, still on Namecheap nameservers). apothecary.rosettawang.org never got past a certificate error, so no link to it exists and it is dropped rather than migrated. That is why the domain-move spec is closed: its one Netlify click is no longer needed.
  • The port is smaller than it looked. The draft said auth.js was the one handler on Node's https. It is eleven of twelve, plus crypto, Buffer and querystring. That used to argue for a rewrite. It no longer does: from compatibility date 2026-08-04 Workers turn on nodejs_compat by default, with node:https and an auto-populated process.env. So the handlers can run as they are behind a thin adapter, which also keeps the house rule of raw https and no SDKs.
  • The double-send risk gets fixed in code, not managed by careful ordering. See the reminders section.
  • The draft's three decisions are made, because each is cheap to reverse: one Worker with a router, keep the /.netlify/functions/ paths, KV for the query log.

The shape

  • wrangler.jsonc: name forest-apothecary, main: src/worker.js, compatibility date 2026-09-30, assets from the repo root with binding ASSETS, not_found_handling: "404-page", run_worker_first: ["/.netlify/functions/*"], one KV binding QUERIES, cron */15 * * * *, vars SITE_URL and STRIPE_TAX_ENABLED, and custom domains for the apex and www (added in phase 5, not before).
  • .assetsignore keeps internals off the site: specs/, scripts/, netlify/, src/, .claude/, CLAUDE.md, *.sql, package*.json, wrangler.jsonc, netlify.toml. This replaces the forced-redirect workaround in netlify.toml, and unlike it, the files are never uploaded at all. Verify with a 404, same as last time.
  • src/worker.js: a router from the path segment after /.netlify/functions/ to each handler, and an adapter both ways. Request becomes { httpMethod, headers, body, queryStringParameters, path, isBase64Encoded: false } with headers lowercased and the body read once as text, which the webhook signature needs byte for byte. { statusCode, headers, body } becomes a Response. Unknown function name is a 404. www gets a 301 to the apex. The scheduled handler calls send-reminders.

Reminders can no longer double-send

send-reminders reads every due row, sends, then marks it. Two runners overlapping, which is exactly what happens during cutover while both Netlify's schedule and the Cloudflare cron exist, would both read the same rows and text the same people twice. The Sep 21 draft handled this by ordering steps carefully. The better fix is to claim before sending: PATCH each row with a filter on its current send_at and sent=false, with Prefer: return=representation, and only send if the PATCH came back with a row. The runner that loses the race gets an empty array and moves on. The daily requeue already writes a new send_at, so the claim is that same write moved before the send, and one-shot rows set sent=true first.

The cost: if Twilio fails after the claim, that reminder is skipped rather than retried. Today a failed one-shot is already marked sent regardless, so this only changes behaviour for a daily reminder on a Twilio outage, which loses one day. Acceptable. Ship it to Netlify first, in phase 3, so both runners have it before both exist.

Notes for whoever drives this

  • Checkout origins. create-checkout-session.js sends buyers back to an allowlisted Origin. In phase 6, drop the workers.dev and tea.laurelate.com entries.
  • Imported DNS. Adding a zone makes Cloudflare import what Namecheap had, including a www CNAME to the parking page. A custom domain cannot be created over an existing CNAME, so those records must go at zone setup.
  • support.js is generated from a dc-runtime/ that is not in this repo. This plan never edits index.html, which is why the /.netlify/functions/ paths stay.
