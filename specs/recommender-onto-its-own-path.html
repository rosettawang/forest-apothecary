Moving the recommender onto its own path

Status: open, not started · written Oct 2, 2026 against the live Worker and the laurelate.com DNS zone

Goal: the herbalist recommender answers at apothecaryforest.com/recommend, and tea.laurelate.com stops existing. The root of the new domain is freed for whatever the Apothecary should actually open with.

This is not a file move, because the app addresses its assets relatively

index.html holds 20 relative references: src="./support.js", src="assets/flower.png", url('assets/texture-baked.jpg?v=2') and so on. Those resolve against the directory the page is served from. Move the file to /recommend/ untouched and every one of them starts asking for /recommend/support.js and /recommend/assets/…, none of which exist. The app would load as an unstyled blank page with no runtime.

One <base href="/"> in the head fixes all 20 at once. That is the recommended answer, and it matters that it is one line: the Worker's own comment records that index.html is generated from a dc-runtime source that is not in this repo, so every hand-edit to it is a patch living on borrowed time. A single obvious line survives a regeneration review. Twenty rewritten paths do not.

The shape of it

  1. Move index.html to recommend/index.html and add <base href="/"> as the first element of its head, before any tag that references an asset. Order matters: a base after a link does not apply to it.
  2. Leave every asset where it is. support.js and assets/ stay at the root, which is what the base tag now points at, and which is also what the static shop and notes pages already use.
  3. Add two rules to src/worker.js, next to the existing www. rewrite:
    • tea.laurelate.com/* returns a 301 to https://apothecaryforest.com/recommend.
    • / on the apex returns a 302 to /recommend, until a home page exists.
  4. Update sitemap.xml and robots.txt, which currently name the old root.
  5. Prove it on workers.dev before any DNS changes. The move, the base tag and both rules are all testable there.

Why the 302 at the root is deliberate

A 301 is cached by browsers aggressively and often indefinitely. Put one on / now and the day a real home page ships, every returning visitor still bounces to /recommend from their own cache, with nothing you can deploy to stop it. The 302 says the same thing to a crawler for this purpose and costs nothing later.

Retiring tea.laurelate.com

The redirect has to come from somewhere, and the obvious host is the one being switched off. If the 301 lived on the Netlify site, Netlify would have to stay alive to serve it, which is the opposite of what the Cloudflare move is for. So tea.laurelate.com is added as a custom domain on the Worker, the Worker answers it with the 301, and Netlify can be retired on schedule.

After 30 days, delete the tea CNAME from the laurelate.com zone. At that point the hostname stops resolving and old links fail, which is the clean break, just taken in two steps rather than one so that nobody following a bookmark in week one hits nothing.
