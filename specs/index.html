Decisions

7 decisions across 2 specs, generated from each spec's spec-decision meta. Answer one and it disappears from here on the next prune.

  • Selling the Thanaka Aftershave · SEO and Stripe
    • Hosted Stripe Checkout or the custom Payment Element? Recommendation: hosted. It brings shipping address collection, Stripe Tax, SCA and Apple/Google Pay at no build cost and keeps PCI scope at nothing. Blocks the checkout build.
    • Laurelate's existing Stripe account or a new Forest Apothecary one? Recommendation: keep Laurelate and set statement_descriptor_suffix, so the card line does not read only LAURELATE to someone who bought from the Apothecary. Revisit if the Apothecary starts carrying its own catalogue. Does not block.
    • Does a shippable product share the existing pickup cart, or get its own flow? Recommendation: separate. The current cart assumes every line is collected at the counter, and merging later is easy while un-merging is not. Blocks the cart work but not the single-product page.
    • Natural preservative system or phenoxyethanol for the lotion? Affects the formula spec and the brand story, not the code. Does not block anything in this spec.
  • Taking the Apothecary off Netlify and onto Cloudflare
    • One Worker with a router, or ten Workers? Recommended: ONE, with a path router. Workers has no one-file-per-endpoint convention the way Netlify Functions does, and ten Workers would mean ten deploys, ten secret sets and ten dashboard entries for what is one app. The cost is that a syntax error takes all ten endpoints down instead of one, which is what the build step is for. Cheap to reverse early, expensive later. Does not block.
    • Keep the /.netlify/functions/ URL shape, or move to /api/? Recommended: KEEP IT, at least through cutover. index.html reaches the backend through exactly two strings - a base at line 1015 and one hardcoded chat path at line 956 - so either choice is a small edit, BUT index.html is a generated artifact (see the support.js risk) and not editing it at all is worth more than a tidy URL. Rename in a later pass once the Worker is proven. Does not block.
    • Netlify Blobs replacement: KV or R2? Recommended: KV. The store is used in exactly two places for one purpose - chat.js writes a query log under a timestamp-plus-random key with setJSON, get-logs.js reads them back - which is a key-value store with small JSON values and no listing requirements beyond a prefix scan. R2 would be object storage for something that is not objects. Does not block.

Spec pass

Spec pass, how specs get worked by default. A session runs the whole thing without asking what to do next.

  1. Reassess the spec first. A spec is a starting point, not a contract. Check its claims against the current code, schema and live state before building. Specs here go stale. Where reality has moved, correct the spec and say what changed.
  2. Sequence it, then work the sequence end to end. Do not stop after one item to report progress, and do not ask which item to do next.
  3. Use discretion to build it out. Fill gaps the spec left, fix what it got wrong, improve on it where the better design is clear. Note the deviations.
  4. Stop only at a blocker or a decision: credentials, a dashboard, an account, content only Rosetta can write, or a choice that is structural and hard to reverse. Not on mere uncertainty. If a call is cheap and reversible, make it, note it, keep going. Stopping means stopping that spec, never the session.
  5. Log the stop in that spec's <meta name="spec-blocker">, dated, then run npm run specs:prune so the index reflects it. A blocker must name a human, a credential or an account. "Revisit later" is parked, not blocked, and a later run that reads it as a blocker will end early believing it is finished.
  6. Declare each decision separately, one <meta name="spec-decision"> per choice, stating the recommended answer and whether it blocks. The prune collects these into the index. Write the meta when you notice the decision, not when you finish the spec. A decision with no recommendation is a question, and a question is harder to answer than a proposal.

spec-needs takes the names of other specs, and spec-touches takes paths. Both are parsed, so prose in either produces nonsense in the derived order.
